# 先定，再说

状态：已提供可选实现（2026-10-20），Runtime 0.19.0。阶段 1 位于默认关闭的
`xiaoyou.decide_first` 开关后；Mac 基线采集和实机验收尚未完成，目前不是默认通道。
主人要求重新设计 Runtime 怎么让小幽说的和做的对得上。它必须满足
[跨端可靠性规则](cross-stack-reliability.zh_CN.md)，尤其是 3 秒首响应的约定。

## 起因

主人手机上的一段录屏（App 0.25.1，Runtime 0.18.1），录的是一轮对话：主人问“再看看这一个月的事情吧?”，
小幽把活交给 `project` 帮手，之后转述它的结果。录屏里有三个问题：

| 看到的 | 原因 | 修在 |
| --- | --- | --- |
| 连着两句确认（“好，我让 project…”接着“好嘞，已经让 project…”） | 带工具说话时，交办成功后循环又问了她一轮，她把说过的话换个说法再说一遍 | Runtime 0.18.2（`dsh_stream.run`：她已经开口、交办又成功了，这一轮就结束） |
| 转述结果在写的过程中出现两三份，每份下面各挂一张任务卡 | Runtime 把正在写的话同时作为消息 `<run>-summary:reply` 和卡上的 `summary_partial` 发出，App 两份都画了 | App 0.25.2（`ChatHistory`：只有没有那条消息时才用卡上那份） |
| 一件事的每条回复下面都挂一张任务卡 | `chatRow` 给已交办的卡的每条小幽消息都挂了卡 | App 0.25.2（卡只挂在这件事最新的那条回复下面） |
| 一条回复的第二个气泡消失半秒又出来 | 任务状态一变就重建那一行，气泡淡入重放（第二个气泡要等 450 ms） | App 0.25.2（原地重建的行不再重新淡入） |

Runtime 0.18.2 的修法是临时补丁，和下面说的提醒机制是同一类。这份设计会把两者都替换掉。

## 提醒机制的问题

从 Runtime 0.16.0 起，她带工具说话时（`dsh_stream.run` 加 `voice_tools.Toolbox`），Runtime 会用正则
（`PROMISE`、`MEMORY_PROMISE`、`LATER_PROMISE`）检查她说完的话。听起来像承诺、又没调对应的工具，
就加一条隐藏的用户消息（`PROMISE_NUDGE`），让她再来一轮。

- **太晚了。** 检查在她的话已经流到手机上之后才做。它能补上漏掉的工具调用，但收不回主人已经看到的话。
  每个副作用都要单独打补丁：0.18.1 丢掉她回应提醒的话，0.18.2 在交办后不再多问一轮。
- **用正则判断她的意思。** 建议（“你可以交给 codex”）和常见说法（“以后我…”“下次就…”）会被误判，
  换个说法的承诺又抓不到。
- **会话被污染。** 提醒以用户消息的身份存进她的工具会话。她会回应它（“说得对，现在补上”），prompt 又得禁止，
  后面几轮她还会从中学到东西。
- **多一轮模型请求**（延迟和费用），而且偏偏出在她答应了事的那几轮。

根本原因在结构上：说的话和做的事是两份各自独立的输出，而话在任何决定做出之前就流出去了。她可以说
自己在做一件还没发生的事。

## 还要收集的数据（阶段 0）

10-20 晚上以后的手机对话只在 Mac 的 Runtime 上。Windows 这份没有工具会话，日志停在 10-17。
改行为之前，先在 Mac 上收集：

```bash
python3 tools/reminder_stats.py <config_dir 或 workdir>/xiaoyou-stream-sessions \
  --log runtime/state/runtime-stderr.log
```

脚本只读，只输出计数：

- **轮数：** 一共多少轮。
- **交办：** 交办了几次，其中几次交办前已经开口。
- **交办后再说：** 交办后又说话的次数（也就是两句确认）。
- **提醒：** 触发了几次，之后有没有调工具、有没有调做事的工具。
- **首字时间：** stderr 日志里 `first_text` 的 p50/p95/max。

局限：

- 每个会话文件只留最新 40 条消息。
- stderr 日志每次启动 Runtime 都会被覆盖。
- 提醒本身不记日志。

首字时间、总时间。不记录消息原文。

## 设计

### 每轮分两步

1. **定（D）。** 用同一个模型、同样的上下文发一次不流式的短请求，只给*承诺类*工具：
   - `start_task`、`amend_task`、`cancel_task`；
   - `remember`、`replace`、`forget`；
   - `track`、`resolve`；
   - 新增的 `just_reply`，表示“这一轮不做承诺”。

   请求要求恰好做一个决定（提供方支持时用 `tool_choice: any`，否则用 prompt 规定，并把“没调工具”当成
   `just_reply`）。Runtime 用已有的检查（`_plan`，经由 `Toolbox.check`）把关并执行这个承诺：建卡、写记忆、
   记下答应的事。检查没通过，失败原因作为事实交给第 2 步。
2. **说（S）。** 主人看到的那次流式请求。它拿到一句第 1 步做了什么的事实陈述（“这一轮：把「回顾近一个月做的事」
   交给了 project”或“这一轮：没有开始任何事，也没记任何东西”）。它只有*查看类*工具（`task_detail`、`recall`；
   `Toolbox(only=…)` 已经有了）。它开始不了任何事，所以说的是已经发生的事，而不是承诺；任务卡仍是交办看得见的记录。

查看类工具故意留在第 2 步：“我看一眼”不是承诺，可以马上流出去。

### 删掉什么

- 作为触发条件的 `PROMISE`、`MEMORY_PROMISE`、`LATER_PROMISE`，`PROMISE_NUDGE`，`dsh_stream.run` 里的
  `nudged` 分支，0.18.2 的交办后即停规则，以及工具结果里 `RECORDED` 那句“用一句话告诉主人”。
- 正则可以留下，但只当统计计数（“话听起来像承诺，第 1 步却选了 `just_reply`”），不再拿它让她重来。

### 3 秒预算

第 1 步在关键路径上，而任务卡不算首响应。目标分配如下：

| 阶段 | 预算 |
| --- | --- |
| 发送、传输、排队、上下文 | ≤ 0.6 秒 |
| D：决定请求 | ≤ 1.2 秒 |
| S：首段正文 | ≤ 0.9 秒 |
| 转发和渲染 | ≤ 0.3 秒 |

这些是目标，不是实测。能不能达到由阶段 0/1 的数据决定。

达不到的话，有两种退路保住约定，按实测选：

- **超时退路。** 给 D 一个硬性时限（约 1.3 秒）。超时就立刻开始 S，并要求“还没开始任何事，别说你在做；
  要么问，要么直接答”。当前可选实现直接丢弃迟到决定，不执行它；未来若允许后台承诺，
  必须先明确对齐状态，说话阶段才能声称已经发生。
- **并行开始。** D 和 S 同时开始；S 一开始只有查看类工具，同样遵守“还没开始任何事”。用一点表达力换延迟。

### 不受影响的路径

- 用 JSON 回答的代理（`reply` 和 `action` 在同一个对象里）本来就一致，照旧走现在的路。
- 转述帮手结果（`_relay`）现在没有承诺类工具，保持不变。
- 后台整理记忆那一轮本来就只有记忆工具（`Toolbox(only=…)`），也不对谁说话。
- 主动唤醒（`proactive.py`）如果能开始做事，应该用同样的 D/S 两步。阶段 1 时核对它的工具集。

### 待定问题

- DeepSeek 的 Anthropic 兼容接口认不认 `tool_choice`（`any` 或指定工具），要发真实请求确认，不要想当然。
- D 能不能用比 S 更小、更快的模型而不降低决定的质量。
- 承诺被拒（比如没有这个帮手）时，S 该怎么说，让主人得到一句清楚的话，而不是来回道歉。
