# 统一消息结构

状态：结构已定（2026-10-16，主人确认“尽量按统一结构走”）。同一天对照本地代码复核了一遍，
补了“统一写入口”“来源接入”“手机上的多台 Runtime”三部分，并重排了实施步骤；又按“小幽是统一
主体”加了预留（暂不实现）。进度见文末。
和[三端可靠性准则](cross-stack-reliability.zh_CN.md)的“多端消息一致性契约”配套：那份说要达到
什么，这份说数据长什么样、各端怎么接。

## 一句话

每台 Runtime 上有一份按对话排好的**消息日志**，它是唯一的权威记录。日志只能经过一个模块写，
就是**记录中心**。卡、给模型的上下文、手机上的聊天记录、设备屏幕上的窗口，都是从这份日志算出来的
**投影**，可以丢掉重建。各端之间、以后新接进来的 Runtime、agent 或外部来源，都只通过这份日志的
格式和同步接口交换内容；**只认编号，不认文字**。

## 为什么要定这个

在这之前，同一句话被存成了好几份，各自有一套编号，靠合并规则对齐：

| 位置 | 存成什么 | 怎么认 |
| --- | --- | --- |
| Runtime 消息记录 | 一次请求（问 + 状态 + 回复） | 消息编号 |
| Runtime 卡 | 卡上的两个条目 | 消息编号 + `:you` / `:reply` |
| Runtime transcript | 给模型续上下文的“一轮” | 另一套轮次编号 |
| 手机 ChatHistory | 一份自己的时间线 | 条目编号；老数据按“文字相同、时间差 120 秒内”猜 |
| 手机旧聊天列表 | `"我：……"` 纯文字行 | 没有编号 |
| 手机 ChatTurn | 换电脑时带过去的问答对 | 又一套编号 |
| 设备 | 最近 12 张卡 | 手机映射的短编号 |

后果：没有一方说了算；相同文字会被合错；编号（`c1`、`c2`）只在一台电脑里唯一；每多一种
显示方式就多一份要单独同步的副本。

## 现在的架构（2026-10-16 对照代码）

> 这一节记的是 Runtime 0.9.0 之前的样子，问题已按下面的“目标架构”和实施步骤处理，见文末进度表。

先回答“现在有没有一个统一管理的模块”：**有一份统一的记录，但还没有统一的写入口。**

```text
                        ┌─────────────── Runtime 进程 ───────────────┐
 手机 ──HTTP──► server.py ──► Service ──┬─► ledger.py   state/messages.json   收下的请求、去重
                                        │
                     xiaoyou.py（26 处）┼─► Cards ──► MessageLog  state/cards.log.jsonl  权威日志
                     service.py（18 处）┤     │                    state/cards.json       卡（副本）
                desktop_sync.py（4 处） ┤     └─ 发序号、持锁
                    artifacts.py（1 处）┘
                                        ├─► store.py    state/transcript.json  给模型的上下文（另一份）
                                        └─► approvals   内存里的授权，不取序号
                        └────────────────────────────────────────────┘
```

做到了的：

- `MessageLog`（`message_log.py`）是每句话的权威记录，带 `runtime_id`、`epoch`、`floor`。
- `Cards`（`cards.py`）是日志的唯一持有者：日志由它的锁保护，序号也由它发。卡上的 `entries`
  启动时以日志为准。
- `/v1/info`、`/v1/sync` 和一致性测试都已经实现。

还没做到的，也是多端一直对不齐的原因：

1. **写的地方太散。** 4 个模块直接调用 `Cards.open/update`，一共 49 处。`update` 有十来个
   可选参数，消息编号、`kind`、`author` 由每个调用方自己拼。有一处拼错，就会产生一条“合法但
   对不上”的消息，日志本身拦不住。
2. **序号有一部分是手动取的。** `Service` 里有 7 处自己调 `cards.bump()` 给请求记录取序号。漏调
   一处，那次变化就不会唤醒等待中的同步。
3. **授权不在日志里，也不取序号。** `/v1/sync` 每次返回的是“现在还在等的授权”的完整列表。一个
   授权如果在两次同步之间出现又消失（比如在电脑上点掉了），手机永远不知道它存在过，也没有记录
   是谁、在哪里答的。前一版文档说“消息、事、授权共用一个计数器”，这一点和代码不符。
4. **还有两份记录和日志并存。** `messages.json`（请求记录）只在收下和去重时用，问题不大；
   `transcript.json`（给模型的上下文）是独立的另一份。在它改成从日志算出来之前，小幽记得的内容
   和手机上看到的可能不一样。
5. **电脑会话的状态映射不对。** `desktop_sync.py` 把电脑会话的 `idle`（这一轮说完了）映射成卡的
   `done`，手机就显示“完成”，其实只是“本轮结束”。

## 目标架构：记录中心

在 `Cards` 和 `MessageLog` 外面收一层，叫**记录中心**（暂定 `record.py` 里的 `Record`）。它是
Runtime 里唯一能改记录的地方：

```text
   来源（谁在产生内容）                    记录中心 Record                     投影（谁在读）
 ┌──────────────────────┐          ┌──────────────────────────┐        ┌──────────────────────┐
 │ 手机发来的消息        │─事件────►│ 一把锁、一个计数器         │──────►│ 卡 / 旧 /v1/feed      │
 │ 小幽（dsh）           │          │ 生成编号、校验字段         │──────►│ /v1/sync              │
 │ Runtime 起的 agent    │          │ 先落盘再确认               │──────►│ 给模型的上下文         │
 │ 电脑上观察到的会话     │          │ 消息 / 事 / 授权 都进日志   │──────►│ 电脑端共享历史         │
 │ 外部上报（网页版等）   │          │ runtime_id、epoch、floor   │──────►│ 等待中的同步（唤醒）   │
 └──────────────────────┘          └──────────────────────────┘        └──────────────────────┘
```

规则：

- **只收事件，不收拼好的记录。** 调用方只说发生了什么，编号、`kind`、`author`、序号都由记录中心
  决定。事件就这几种：

  | 事件 | 谁发 | 结果 |
  | --- | --- | --- |
  | `accept(conversation, text, client_id)` | Service 收下手机的话 | 主人的一条消息，落盘后才返回 |
  | `reply_started / reply_partial / reply_final / reply_failed` | 小幽、agent 适配器 | 小幽或帮手的一条回答，`partial` 不落盘 |
  | `task_open / task_progress / task_state` | Service、agent 适配器 | 一件事和它的状态 |
  | `approval_open / approval_closed(by, where)` | 授权桥、电脑端审批 | 授权进日志、取序号，关掉时记下是谁、在哪答的 |
  | `observed(source, upstream_id, …)` | 电脑会话观察器 | 只读消息，编号取自上游记录 |
  | `reported(source, upstream_id, …)` | 外部上报接口 | 只读消息，编号取自上报方给的编号 |
  | `note(conversation, text)` | Runtime 自己 | “Runtime 重启了”这类提示 |

- **所有改动都在一把锁里取一个序号、追加到日志、唤醒等待者。** 不再有单独的 `bump()` 给外面调。
- **投影只读。** 卡、transcript、共享历史都订阅记录中心的变化，自己不写日志。坏了可以从日志重建。
- **`Cards` 退回成投影**，`MessageLog` 和 `ledger.py` 成为记录中心内部的存储，不再被外面直接用。

这样“统一管理”就落在一个模块上：要知道一句话怎么来的、为什么是这个状态，只看记录中心的事件。

## 记录长什么样

### 身份

- `subject_id`：**小幽这个主体**的编号，和跑在哪台电脑上无关。对话、记忆、人设都属于主体，
  不属于某台 Runtime。现在只有一个主体，第一次启动时生成并存进 state 目录；把 state 目录搬到
  另一台电脑，主体跟着走。见“统一主体（预留）”。
- `runtime_id`：每台 Runtime 第一次启动时生成，存在 state 目录里，之后不变。换一台电脑或
  虚拟机就是新的 `runtime_id`。它说明一条记录是**在哪里产生的**，不说明属于谁。
- `epoch`：这份记录的编号。记录文件丢了、坏了、被换掉时改变；客户端看到它变了就从头同步。
- 消息编号：在一台 Runtime 里唯一，由记录中心生成。主人说的话是 `<请求编号>:you`，小幽对它
  的回答是 `<请求编号>:reply`（沿用现在卡条目的编号）；后台结果、转述等用
  `<任务运行编号>-result:reply` 这一类规则生成；观察到的和外部上报的，用来源加上游编号生成。
  **全局编号 = `runtime_id` + `/` + 消息编号**，跨电脑也不会撞。
- `client_id`：手机发消息时自己生成，只用来防重复提交（按对话算），收下后对应到消息编号。
  手机上“还没发出去”的消息只用它。

### 消息（Message）

| 字段 | 含义 |
| --- | --- |
| `id` | 消息编号（见上） |
| `conversation` | 所属对话 |
| `task` | 所属的事（卡号）；闲聊没有 |
| `scope` | `main`（主对话里）或 `task`（在某件事里面说的） |
| `author` | `{kind, name}`：`owner`（主人）、`xiaoyou`、`agent`（某个帮手）、`desktop`（电脑上观察到的会话）、`external`（外部上报） |
| `kind` | `user`、`reply`、`handoff`、`result`、`summary`、`note`（如“Runtime 重启了”） |
| `reply_to` | 回答的是哪条消息 |
| `text` / `partial` | 定稿文字 / 还在生成的整段（整段替换；空串表示收回） |
| `status` | `queued`、`streaming`、`final`、`failed`、`cancelled` |
| `source` | `{type, session_id?, runtime_id?, origin?}`：`runtime`（本机产生）、`desktop`（观察来的，只读，带 `session_id`）、`external`（外部上报，只读，带 `origin` 和 `session_id`）、`imported`（从别的 Runtime 带过来的历史，带原来的 `runtime_id`）。**存盘时每条都写产生它的 `runtime_id`**，这样日志搬到别处或和别处合并时不会认错；同步回答里本机产生的可以省略，顶层已经有 |
| `attachments` | 附件编号 |
| `created_at`、`rev`、`seq` | 创建时间、这条的修订号（只增不减，跨重启也是；实现上直接用序号）、日志序号 |

### 事（Task，现在叫卡）

事是消息的分组：编号、对话、标题、状态、谁在做、进展、成员消息的编号列表、用量。为兼容现有
客户端，卡里仍然带一份成员消息的副本（`entries`）；它是投影，不另算一份记录。

状态要把“这一轮说完了”和“整件事做完了”分开：

| 状态 | 含义 |
| --- | --- |
| `working` | 正在做 |
| `waiting` | 等授权或等主人回话 |
| `turn_ended` | 这一轮说完了，事还没完（电脑会话 `idle` 映射到这里） |
| `done` / `failed` / `cancelled` | 整件事结束 |
| `unavailable` | 暂时看不到它的状态（比如观察的来源很久没有更新） |

旧 App 不认识 `turn_ended`，`/v1/feed` 这个投影给旧 App 时仍然映射成 `done`，`/v1/sync` 给真实状态。

### 授权（Approval）

授权也是日志里的一条记录，每次变化取一个序号：编号、所属的事、谁要的、要做什么、状态（`pending`、
`allowed`、`denied`、`expired`、`withdrawn`）、谁答的（`phone`、`desktop`、`device`）。手机按序号增量
拿，出现又消失的授权也能看到它的结局。

### 日志和序号

消息、事、授权的每一次变化都在记录中心里从同一个计数器取一个 `seq`。在同一个 `epoch` 里 `seq`
只增不减，重启也一样；只保证越来越大，不保证连续。

日志存在 `state/cards.log.jsonl`（一行一条记录的最新样子，追加写），最多留 5000 条消息。超出时挤掉
最早的、已经不在任何卡上的消息。**挤掉不是删除**：不发墓碑，客户端缓存里的旧消息照留，否则手机上的
聊天记录会跟着 Runtime 的裁剪消失。被挤掉的最大序号记成 `floor`，游标比它还旧的客户端会被要求重拉
快照。只有将来主动删除消息时，才会出现在 `removed` 里。

## 同步接口：新的 Runtime 只要实现这个就能接进来

| 接口 | 契约 |
| --- | --- |
| `GET /v1/info`（要令牌） | 返回 `subject_id`、`runtime_id`、`epoch`、`protocol`、`capabilities`、`name`、`version`。`/healthz` 不需要令牌，所以不放这些 |
| `POST /v1/messages`（带 `client_id`） | 落盘后才回 `202`；同一对话同一 `client_id`：内容相同返回原消息，不同返回 `409`；写不下去 `503` |
| `GET /v1/sync?conversation=&after=&epoch=&wait=` | 返回 `{runtime_id, epoch, seq, messages, tasks, approvals, removed, more, reset}`；`after=0` 是全量快照；`epoch` 不对、`after` 比现在的 `seq` 还大、或者早于 `floor` 时 `reset: true`，并从 0 给快照。事（`tasks`）是卡去掉 `entries`、换成成员编号 `members`。`approvals` 改成按序号的增量（见上）。快照和后续增量之间不能漏 |
| `POST /v1/approvals/<编号>` | 回答授权，不变 |
| `POST /v1/reports`（要令牌，新增） | 外部来源上报进展，见下一节 |

客户端规则：先应用、再推进游标；**游标当作看不懂的字符串原样存、原样带回**，不做加减比较
（现在它是一个数字，以后多台 Runtime 共用一个主体时可能变成多段，客户端不用改）；按全局编号合并；`rev` 大的赢；定稿不会被 `partial` 覆盖；
看不懂的可选字段忽略，看不懂的必需结构要求升级。现有的 `/v1/feed` 保留，作为旧 App 用的
投影，不再加新东西。

## 来源接入：哪些会话能进来

手机上能看到的“别处的会话”分三种，能力不一样，要在界面上说清楚：

| 来源 | 怎么进来 | 能做什么 | 现状 |
| --- | --- | --- | --- |
| Runtime 自己起的 agent（`claude`、`codex`、`tailor`…） | agent 适配器发事件 | 看、追加、取消、授权 | 已有 |
| 电脑上主人自己开的 Claude Code、Codex 会话 | 观察器每秒读本机的转录文件 | 只读；可选审批桥 | 已有；发现新会话约 2 秒，`idle` 映射要改 |
| **不在这台电脑上的会话**：claude.ai 网页版、云端 Claude Code、别人的电脑 | 本机没有它们的转录文件，观察器**读不到** | 只读，靠对方主动上报 | **没有** |

第三种是“App 看不到网页版 Claude 在做什么”的原因。网页版 Claude 的对话存在 claude.ai 上，
Runtime 没有能力去读。方案是开一个上报接口，让对方主动报：

- `POST /v1/reports`：`{origin, session_id, title?, state, text?, upstream_id, at}`。`origin` 是来源名字
  （如 `claude-web`），`upstream_id` 由上报方给、同一条重复报不会重复记。记录中心把它记成
  `source: external` 的只读消息，挂在一件“外部会话”的事上。
- 上报方怎么报：网页版 Claude 在主人的 Mac 上能跑命令时，在它的项目说明里约定“开始、阶段完成、
  结束时跑一次 `python3 -m xiaoyou_runtime.report …`”。跑不了命令的来源就接不进来，手机上也不假装
  能看到。
- 上报的内容只读，不能从手机续聊；状态超过一段时间没更新就显示 `unavailable`，不显示“完成”。

## 手机上的多台 Runtime

现在手机同一时间只跟着选中的那一台 Runtime：切换时清空卡片、从头拉取
（`RuntimeClient.java` 里的 `selectedRuntime` 和 `resetCards`）。手机按地址认电脑，所以同一台 Mac 的
局域网地址和 Funnel 地址会被当成两台。新的规则：

1. **按 `runtime_id` 认电脑，不按地址。** 添加地址时先调 `/v1/info`，同一个 `runtime_id` 的多个地址
   归到同一台电脑下，连不上一个就换另一个，不清空数据。
2. **每台电脑一份本地缓存和一个游标**，以 `runtime_id` 为键。切换显示的电脑时不清空，切回来接着
   增量拉。
3. **先只同步选中的那一台，后台的电脑只拉一次摘要**（有没有等授权、有没有新结果），在侧边栏
   显示小红点。多台同时完整同步放到以后，看实际需要再做。
4. 同一句话只存在于它所在的那台 Runtime 上；手机合并显示时按全局编号区分，不跨电脑合并。

## 统一主体（预留，暂不实现）

产品上的核心概念是：**小幽是一个统一的主体**。不管小幽的服务跑在哪台电脑、哪台云主机上，
主人面对的都是同一个小幽、同一套对话。上面“多台 Runtime”那一节只是让手机能同时连几台电脑，
每台各有各的记录；统一主体要的是“几台电脑上的小幽，是同一个小幽”。

现在先不做，但下面这些现在就要按它来，免得以后要迁移数据或改 App：

| 预留 | 现在怎么做 | 为什么 |
| --- | --- | --- |
| 主体编号 | `subject_id` 和 `runtime_id` 分开；`/v1/info` 返回两者 | 以后换电脑跑，主体不变，手机认的是主体 |
| 记录带产地 | 日志里每条都写产生它的 `runtime_id`，不省略 | 日志可以搬家，也可以和别处的合并，编号不会撞也不会认错 |
| 编号不依赖本机 | 全局编号 = 产地 `runtime_id` + 消息编号；不用“本机第几条”当身份 | 同上 |
| 游标不透明 | 客户端把游标当字符串原样带回 | 以后游标可以变成“每个产地一段”，App 不用改 |
| 来源走事件 | 远处的 Runtime 也只是一个来源，通过和本机 agent 一样的事件（第一层）报给记录中心 | 跨电脑和本机用同一套标准，不另起一套协议 |
| 对话、记忆属于主体 | transcript、会话编号、人设都按主体存，不按电脑存（第 4 步一起做） | 换电脑后小幽记得之前的事 |

以后真要做的时候，打算这样：

- **主体有一个“家”**：一台 Runtime 持有这个主体的权威日志，叫主 Runtime。家可以搬，比如把
  state 目录迁到另一台电脑，或者用导出、导入的方式迁过去。手机只连家。
- **其他电脑上的 Runtime 是“分身”**：它们照样能起 agent、观察本机会话，但不另存一份主体记录，
  而是把事件报回家里（类似外部上报，但能力更全：追加、取消、授权都能转回去）。
- 家里离线时，分身先在本地记下，回来后按产地编号补交，不会重复，也不会撞号。

这几条要等真有第二台电脑长期跑小幽时再细化，现在只保证上面的预留不被破坏。

## 各端是哪种投影

| 投影 | 从日志算什么 | 能写什么 |
| --- | --- | --- |
| Runtime 的卡、旧 `/v1/feed` | 按事分组的消息和状态 | 不能写，由记录中心写日志 |
| 给模型的上下文（transcript） | 最近的定稿消息；`imported` 的标明来源 | 不能写 |
| 电脑端共享历史 | 同上，给电脑上的 agent 看 | 不能写 |
| 手机聊天和任务 | 每台 Runtime 一份日志的本地缓存（按全局编号存）＋还没发出去的消息 | 只能发新消息、回答授权、取消 |
| 设备屏幕 | 手机给的最近窗口；手机负责把全局编号映射成设备的短编号 | 按键、语音经手机变成发消息 |
| 电脑上观察到的会话、外部上报 | `source: desktop` / `external` 的消息 | 只读 |

## 怎么接入

1. **新的 Runtime**（另一台电脑、云上的虚拟机、或另一种实现）：实现上面的同步接口。手机不需要
   为它写专门的代码，像加一台电脑一样添加；数据按 `runtime_id` 区分，不会和别的电脑撞号。
   接入前先跑一致性测试：`python3 -m xiaoyou_runtime.conformance --url <地址> --token <令牌>`
   （会在一个单独的对话里发两句话，真的调用一次模型）。
2. **新的 agent 接到某台 Runtime 后面**：适配器只向记录中心发“开始了 / 生成到这里了 / 一行进展 /
   要授权 / 做完了 / 失败了”这几种事件（就是现在 `Control` 的那几个回调），并声明能做什么（中途追加、
   取消、续上会话）。编号、序号、落盘、同步都由记录中心负责，agent 不碰。
3. **只能观察的来源**：本机有转录文件的，由观察器发 `observed` 事件；本机没有的，由对方调
   `/v1/reports` 上报。两种都只读，编号取自上游，不能按文字生成。

## 不变的东西

- 同一对话里一句一句按收下的顺序处理；授权的身份和过期规则不变。
- 旧 App 继续用 `/v1/feed`，在它们退役前不删。
- 这是内部结构和协议，不是对外公开的 SDK。
