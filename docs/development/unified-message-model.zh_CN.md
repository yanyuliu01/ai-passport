# 统一消息结构

状态：结构已定（2026-10-16，主人确认“尽量按统一结构走”），分步实施中，进度见文末。
和[三端可靠性准则](cross-stack-reliability.zh_CN.md)的“多端消息一致性契约”配套：那份说要达到
什么，这份说数据长什么样、各端怎么接。

## 一句话

每台 Runtime 上有一份按对话排好的**消息日志**，它是唯一的权威记录。卡、给模型的上下文、
手机上的聊天记录、设备屏幕上的窗口，都是从这份日志算出来的**投影**，可以丢掉重建。各端之间、
以后新接进来的 Runtime 或 agent，都只通过这份日志的格式和同步接口交换内容；**只认编号，
不认文字**。

## 为什么要定这个

在这之前，同一句话被存成了好几份，各自有一套编号，靠合并规则对齐：

| 位置 | 存成什么 | 怎么认 |
| --- | --- | --- |
| Runtime 消息记录 | 一次请求（问 + 状态 + 回复） | 消息编号 |
| Runtime 卡 | 卡上的两个条目 | 消息编号 + `:you` / `:reply` |
| Runtime transcript | 给模型续上下文的“一轮” | 另一套轮次编号 |
| 手机 ChatHistory | 一份自己的时间线 | 条目编号；老数据按“文字相同、时间差 120 秒内”猜 |
| 手机旧聊天列表 | `"我：……"` 纯文字行 | 没有编号 |
| 手机 ChatTurn | 换电脑时带过去的问答对 | 又一套编号 |
| 设备 | 最近 12 张卡 | 手机映射的短编号 |

后果：没有一方说了算；相同文字会被合错；编号（`c1`、`c2`）只在一台电脑里唯一；每多一种
显示方式就多一份要单独同步的副本。

## 记录长什么样

### 身份

- `runtime_id`：每台 Runtime 第一次启动时生成，存在 state 目录里，之后不变。换一台电脑或
  虚拟机就是新的 `runtime_id`。
- `epoch`：这份记录的编号。记录文件丢了、坏了、被换掉时改变；客户端看到它变了就从头同步。
- 消息编号：在一台 Runtime 里唯一，由 Runtime 生成。主人说的话是 `<请求编号>:you`，小幽对它
  的回答是 `<请求编号>:reply`（沿用现在卡条目的编号）；后台结果、转述等由 Runtime 用
  `<任务运行编号>-result:reply` 这一类规则生成。**全局编号 = `runtime_id` + `/` + 消息编号**，
  跨电脑也不会撞。
- `client_id`：手机发消息时自己生成，只用来防重复提交（按对话算），收下后对应到消息编号。
  手机上“还没发出去”的消息只用它。

### 消息（Message）

| 字段 | 含义 |
| --- | --- |
| `id` | 消息编号（见上） |
| `conversation` | 所属对话 |
| `task` | 所属的事（卡号）；闲聊没有 |
| `scope` | `main`（主对话里）或 `task`（在某件事里面说的） |
| `author` | `{kind, name}`：`owner`（主人）、`xiaoyou`、`agent`（某个帮手）、`desktop`（电脑上观察到的会话） |
| `kind` | `user`、`reply`、`handoff`、`result`、`summary`、`note`（如“Runtime 重启了”） |
| `reply_to` | 回答的是哪条消息 |
| `text` / `partial` | 定稿文字 / 还在生成的整段（整段替换；空串表示收回） |
| `status` | `queued`、`streaming`、`final`、`failed`、`cancelled` |
| `source` | `{type, runtime_id, session_id?}`：`runtime`（本机产生）、`desktop`（观察来的，只读）、`imported`（从别的 Runtime 带过来的历史） |
| `attachments` | 附件编号 |
| `created_at`、`rev`、`seq` | 创建时间、这条的修订号、日志序号 |

### 事（Task，现在叫卡）

事是消息的分组：编号、对话、标题、状态（在做 / 等授权 / 结束……）、谁在做、进展、
成员消息的编号列表、用量。为兼容现有客户端，卡里仍然带一份成员消息的副本（`entries`）；
它是投影，不另算一份记录。

### 日志和序号

消息、事、授权的每一次变化都从同一个计数器取一个 `seq`。在同一个 `epoch` 里 `seq` 只增不减，
重启也一样；只保证越来越大，不保证连续。

日志存在 `state/cards.log.jsonl`（一行一条消息的最新样子，追加写），最多留 5000 条。超出时挤掉
最早的、已经不在任何卡上的消息。**挤掉不是删除**：不发墓碑，客户端缓存里的旧消息照留，
否则手机上的聊天记录会跟着 Runtime 的裁剪消失。被挤掉的最大序号记成 `floor`，游标比它还旧的
客户端会被要求重拉快照。只有将来主动删除消息时，才会出现在 `removed` 里。

## 同步接口：新的 Runtime 只要实现这个就能接进来

| 接口 | 契约 |
| --- | --- |
| `GET /v1/info`（要令牌） | 返回 `runtime_id`、`epoch`、`protocol`、`capabilities`、`name`、`version`。`/healthz` 不需要令牌，所以不放这些 |
| `POST /v1/messages`（带 `client_id`） | 落盘后才回 `202`；同一对话同一 `client_id`：内容相同返回原消息，不同返回 `409`；写不下去 `503` |
| `GET /v1/sync?conversation=&after=&epoch=&wait=` | 返回 `{runtime_id, epoch, seq, messages, tasks, approvals, removed, more, reset}`；`after=0` 是全量快照；`epoch` 不对、`after` 比现在的 `seq` 还大、或者早于 `floor` 时 `reset: true`，并从 0 给快照。事（`tasks`）是卡去掉 `entries`、换成成员编号 `members`。快照和后续增量之间不能漏 |
| `POST /v1/approvals/<编号>` | 回答授权，不变 |

客户端规则：先应用、再推进游标；按全局编号合并；`rev` 大的赢；定稿不会被 `partial` 覆盖；
看不懂的可选字段忽略，看不懂的必需结构要求升级。现有的 `/v1/feed` 保留，作为旧 App 用的
投影，不再加新东西。

## 各端是哪种投影

| 投影 | 从日志算什么 | 能写什么 |
| --- | --- | --- |
| Runtime 的卡 | 按事分组的消息和状态 | 不直接写，由 Runtime 写日志 |
| 给模型的上下文（transcript） | 最近的定稿消息；`imported` 的标明来源 | 不能写 |
| 电脑端共享历史 | 同上，给电脑上的 agent 看 | 不能写 |
| 手机聊天和任务 | 日志的本地缓存（按全局编号存）＋还没发出去的消息 | 只能发新消息、回答授权、取消 |
| 设备屏幕 | 手机给的最近窗口；手机负责把全局编号映射成设备的短编号 | 按键、语音经手机变成发消息 |
| 电脑上观察到的会话 | `source: desktop` 的消息，编号来自上游转录记录 | 只读 |

## 怎么接入

1. **新的 Runtime**（另一台电脑、云上的虚拟机、或另一种实现）：实现上面的同步接口。手机不需要
   为它写专门的代码，像加一台电脑一样添加；数据按 `runtime_id` 区分，不会和别的电脑撞号。
   接入前先跑一致性测试：`python3 -m xiaoyou_runtime.conformance --url <地址> --token <令牌>`
   （会在一个单独的对话里发两句话，真的调用一次模型）。
2. **新的 agent 接到某台 Runtime 后面**：适配器只需要报告“开始了 / 生成到这里了 / 一行进展 /
   要授权 / 做完了 / 失败了”（就是现在 `Control` 的那几个回调），并声明能做什么（中途追加、
   取消、续上会话）。编号、序号、落盘、同步都由 Runtime 负责，agent 不碰。
3. **只能观察的来源**（比如电脑上自己开的会话）：产生 `source: desktop` 的只读消息，编号取自
   上游记录，不能按文字生成。

## 不变的东西

- 同一对话里一句一句按收下的顺序处理；授权的身份和过期规则不变。
- 旧 App 继续用 `/v1/feed`，在它们退役前不删。
- 这是内部结构和协议，不是对外公开的 SDK。
