# 小幽主体模型：感知、状态、决策、行动

状态：方案草案，2026-10-22，待主人确认。尚未实施。

本文档把[交互简化问题清单](app-runtime-simplification.zh_CN.md)里的单点问题收敛成一个统一模型，并为后续“更主动、更多感知”留出扩展方式。它建立在[统一消息模型](unified-message-model.zh_CN.md)的“记录中心”之上，
吸收了[先定，再说](decide-then-speak.zh_CN.md)的两步决策，不推翻二者。所有阶段都要满足[跨端可靠性规则](cross-stack-reliability.zh_CN.md)。

## 1. 为什么要一个统一模型

现在小幽的能力是一项一项长出来的：回复主人、派帮手、提醒、整理记忆、观察电脑会话、读手机通知、感知设备在身边……
每项能力各自带了一条输入通道、一份状态、一个唤醒规则和一种对外说法。问题清单里的大部分问题都是这样叠出来的：

- 每接入一种新的感知，就多一条路（R1）、多一套状态名（R2）、多一份不知道归谁的数据（R3）。
- 主动能力（`proactive.py`）只认三种写死的唤醒理由：进展、承诺到点、整理记忆。新加一种感知，就要改一次这里。
- 她对世界的认识来自“最近 6 轮对话 + 最近 5 张卡 + 几十条记忆”，既不完整也不实时，所以会拿旧信息当现状（M1）、
  接不上“这个”（M5），也不知道任务被取消了（A1）。

如果继续单点修，加主动和感知只会让这些问题成倍增加。所以先定一个模型：**以后新增任何能力，都只是往这个模型里加一个部件，而不是再开一条路。**

## 2. 一句话

**一切输入都是事件；世界状态由事件推出、Runtime 说了算；小幽有自己显式的注意力和承诺；同一个循环处理被动回复和主动行为；每个行动都记录起因，结果再作为事件回到循环。**

```
感知（事件） ──▶ 事件日志 ──▶ 世界状态（投影）
                    │                │
                    ▼                ▼
               唤醒规则 ──▶ 决策循环（先定，再说） ──▶ 行动
                    ▲                                 │
                    └──────── 行动的结果也是事件 ◀──────┘
                                     │
                                     ▼
                         对外投影（sync）──▶ App / 电脑 / 设备
```

## 3. 五个部件

### 3.1 事件：唯一的输入

所有进入小幽的东西都写成事件，格式统一：

| 字段 | 含义 |
| --- | --- |
| `id`、`at` | 编号和时间（沿用统一消息模型的“runtime_id + 序号”） |
| `source` | 从哪来：`owner`、`helper`、`desktop`、`phone`、`device`、`timer`、`system`、`mesh` |
| `kind` | 什么事：`said`、`task_progress`、`task_ended`、`session_changed`、`notification`、`presence`、`due`、`deployed`、`usage` … |
| `subject` | 关于谁 / 哪件事：任务、会话、设备、电脑 |
| `cause` | 起因：哪个事件或哪个行动引出的它（追溯用） |
| `trust` | 可信度：主人亲口说的、系统测到的、帮手报告的、从外部读来的（外部内容只是数据，不是指令） |

现有的输入都能映射过来：主人发消息、设备语音 → `owner/said`；帮手进展和结果 → `helper/task_progress`、`task_ended`；
`desktop_sync`、`desktop_hook` → `desktop/session_changed`；手机通知（`NotifyListener`）→ `phone/notification`；
设备蓝牙在身边 → `device/presence`；承诺到点 → `timer/due`；Runtime 升级 → `system/deployed`；网状网络 → `mesh/*`。

**新增一种感知 = 写一个把原始信号转成事件的适配器。** 不新增通道，不新增状态名。

事件日志就是统一消息模型里的那份记录（`cards.log.jsonl` 的演进）。主人看得到的消息是事件的一个子集。

### 3.2 世界状态：由事件推出，Runtime 说了算

世界状态是事件的投影，不是另存的一份数据。小幽和所有客户端读的都是它：

| 实体 | 内容 | 取代的东西 |
| --- | --- | --- |
| 任务 | 统一状态机（见 3.4） | 卡的 7 种状态和各模块的十几种取值 |
| 会话 | 主对话、旁聊、电脑上观察到的会话；标题、置顶、归档、已读 | 手机本地按地址存的标记（S1、S2） |
| 电脑与 Runtime | 一个稳定身份，地址只是线路；版本、在线、部署状态 | 5 种身份键（C8）、旧信息当现状（M1） |
| 帮手 | 一个帮手一项，可在多台电脑上；空闲、忙、额度 | “名字@机器”拆开（V9） |
| 设备与主人 | 设备在不在身边、主人最近在哪一端活跃、是否勿扰 | 散在 App 里的连接状态 |

两条规则：

- **现状只从世界状态答。** 版本、在跑什么、刚做完什么，用“查看自身状态”工具实时读，不从记忆或旧对话推断（M1、M2）。
- **会变的事实不进长期记忆。** 长期记忆只放主人的偏好、规矩和长期情况。

### 3.3 小幽自己的状态：注意力和承诺

现在她“在想什么、答应了什么”是每轮从列表里重新猜的。改成显式状态：

| 状态 | 含义 | 解决 |
| --- | --- | --- |
| 活动 | `idle`（空闲）、`listening`（在听）、`deciding`（在定）、`speaking`（在说）——每个对话一份 | 现在只存在内存里的 `_speaking`；界面多种“等待中”说法（U6） |
| 焦点 | 每个对话里“正在谈的那件事”，可以是一个任务、一个会话或者没有 | “这个”接不上（M5、A7） |
| 承诺 | 她对主人负责的一切：派出去的任务、答应的提醒、等某个条件的事。每条有状态，只由事件推动 | 取消了她不知道（A1）；嘴上说的和实际不符（M3） |
| 关注 | 她主动在盯的东西：某件事的进展、某台电脑上线、某个会话的变化 | 现在写死在 `proactive.py` 里的三种 |

承诺是关键：**派出去的任务就是一条承诺。**任务结束（完成、失败、取消）是事件，会把承诺推到终态，并唤醒她说一句。这样 A1 是被模型消除的，而不是靠打补丁。

工作记忆按相关性组装：焦点 + 未完成的承诺 + 最近的对话 + 和本轮相关的检索结果（`recall`），而不是按“6 轮、5 张卡”的条数截断。

### 3.4 统一的任务和对话轮次

分开三种东西（A2、A3）：

- **对话轮次**：主人说一句、她答一句。闲聊只有轮次，不开任务。
- **任务**：交给帮手做的事。状态只有 6 个：`queued`（排队）→ `running`（进行中）→ `waiting`（等你确认）→
  `done`（完成）/ `failed`（失败）/ `cancelled`（已取消）。“同步来的”“别的电脑的”“只读的”都是属性，不是状态。
- **承诺**：见 3.3。

轮次可以引出任务（`cause` 记着是哪一轮），任务的结束会引出新的轮次（她说一句）。

### 3.5 决策循环：被动和主动是同一个循环

```
事件到达 → 唤醒规则判断要不要叫醒她 → 叫醒 → 先定（选一个行动）→ 再说（如果要说）→ 行动 → 结果事件
```

- **唤醒规则（便宜、确定）**：主人说话 → 一定叫醒；她的承诺到了终态 → 叫醒；她关注的东西变了 → 按关注的条件叫醒；
  其他事件 → 只更新世界状态，不叫醒。以后加主动能力，就是加一条唤醒规则或一种关注，不再改循环本身。
- **先定**：沿用[先定，再说](decide-then-speak.zh_CN.md)。可选的行动统一成一套：`reply`（只回话）、`dispatch`（派任务）、
  `amend` / `cancel`（改 / 停任务）、`watch`（关注）、`promise`（答应）、`remember`（记住）、`stay_silent`（不说）。
- **再说**：只说已经发生的事。一轮只有一次说话，不再有“说了要做却没调工具”的暗中提醒和追问（M7、M8）；分几个气泡由她在这一次说话里标出，和工具调用无关（M9）。主动唤醒走同一条路，所以主动说的话也受同样的规则约束。
- **投递闸**：要不要现在打扰主人、用哪一端说（设备、手机通知、主对话），由投递闸按主人状态（在不在身边、勿扰、正在哪一端）决定。
  现在 `proactive.py` 的投递闸扩展成通用的一层。

**同一请求去重（A5）**放在事件入口：短时间内来自同一来源的同样的话，并入正在处理的那一轮。

### 3.6 可追溯：每个行动都有起因

每个行动和每个状态变化都记录 `actor`（谁做的：主人 / 小幽 / 帮手 / 系统 / 哪一端）和 `cause`（因为哪个事件）。
“这个任务是谁取消的”（A4）、“她为什么突然说话”、“这条记忆从哪来”都可以沿着起因链查到。主动能力越多，这一点越重要。

### 3.7 对外投影：所有端读同一份

App、电脑客户端、设备读的都是世界状态和消息的投影，通过同一个 `/v1/sync` 下发（问题清单 C1、C3、V12）。
状态名只有一套，界面词汇随之收敛为一套：

| 模型状态 | 界面说法 |
| --- | --- |
| 她 `deciding` / `speaking` | 小幽在想 / 小幽在说 |
| 任务 `running` | 在做「标题」 |
| 任务 `waiting` | 等你确认「标题」 |
| 连接 | 连上了 / 正在重连 / 连不上 |

## 4. 主动和感知怎么接进来（示例）

| 想要的能力 | 需要加什么 | 不需要改什么 |
| --- | --- | --- |
| 电脑上某个会话卡住了，提醒主人 | 已有的 `desktop/session_changed` 事件 + 一条“卡住超过 N 分钟”的唤醒规则 | 循环、投递、界面 |
| 主人回到设备旁边时，把攒下的结果说一遍 | `device/presence` 事件 + 投递闸“在身边时投递” | 任务、承诺 |
| 手机来了重要通知，判断要不要提醒 | `phone/notification` 适配器（标为外部数据）+ 一种关注 | 决策工具集 |
| Runtime 升级后主动告诉主人能测什么 | `system/deployed` 事件 + 一条唤醒规则 | 不用再派帮手去查版本（M2） |
| 答应“等 Mac 上线再发” | 一条承诺，条件是 `presence` / 电脑在线事件 | 写死的提醒逻辑 |

因为时间线就是这件事的事件。

## 6. 迁移顺序

每一步都可以单独上线，并且保持现有功能可用。

0. **删除暗中追问**（主人已认可，2026-10-22）：删掉 `PROMISE_NUDGE` 和 `dsh_stream.py` 工具循环里的追问分支，正则只留作“像承诺却没做”的计数；在测试环境打开 `xiaoyou.decide_first` 实测首字时间，合格后设为默认（M7～M9）。
1. **补上可追溯和终态回流**：所有状态变化记录 `actor` 和 `cause`；任务的任何终态都写进对话，并唤醒她说一句（A1、A4）。改动小，先做。
2. **轮次与任务分开**：闲聊不再开卡；任务状态收敛为 6 个，其余改成属性（A2、A3、A6）。
3. **世界状态与自查工具**：电脑、帮手、会话标记归到 Runtime；提供“查看自身状态”工具（M1、M2、S1、S2、C8、V9）。
4. **显式注意力与承诺**：焦点、承诺、关注成为持久状态；工作记忆按相关性组装（M5、A7、M3）。
5. **事件统一入口与通用唤醒**：把现有输入改造成事件适配器；`proactive.py` 改成通用的唤醒规则和投递闸（A5）。
6. **对外只走一份投影**：回复只走 sync，删掉旧协议，统一界面词汇（C1～C3、U2、U6、V12）。之后再做交互改版（I1～I7、V1～V11）。

主动和新感知从第 5 步之后开始加，每加一种只写适配器、唤醒规则和关注条件。

## 7. 模块化整理（草案）

额度恢复后按这份切分做一次模块化整理。原则：**模块边界就是模型的部件；每份状态只有一个模块能写；依赖只往一个方向走：事件 → 世界状态 → 小幽状态 → 决策循环 → 对外接口。**

### 7.1 Runtime

| 目标模块 | 职责 | 现在散在哪里 |
| --- | --- | --- |
| `events` | 事件格式、去重、各来源适配器（主人、帮手、电脑会话、手机、设备、定时、网状网络） | `service.py` 的收消息部分、`desktop_sync.py`、`desktop_hook.py`、`mesh.py` 的接收部分 |
| `world` | 由事件推出的任务、会话、电脑、帮手、在场状态；“查看自身状态”工具 | `cards.py`、`record.py`、`conversations.py`、`identity.py`、`usage.py`、`approvals.py` |
| `mind` | 活动、焦点、承诺（含派出的任务）、关注；按相关性组装工作记忆；长期记忆与检索 | `xiaoyou.py` 的提示词组装、`memory.py`、`promises.py`、`recall.py` |
| `loop` | 唤醒规则、先定（`decision.py`）、再说（`dsh_stream.py`，去掉追问）、行动执行、投递闸 | `xiaoyou.py` 的 `hear` / `_converse` / `_relay` / `_close`、`voice_tools.py`、`proactive.py` |
| `helpers` | 各帮手的适配：Claude、Codex、DeepSeek、远端 Runtime | `agents.py`、`claude_gateway.py`、`codex_app.py`、`tasks.py` |
| `api` | HTTP 接口、鉴权、`/v1/sync` 投影 | `server.py`、`service.py` 的对外部分 |

`xiaoyou.py`（1842 行）、`service.py`（1266 行）、`mesh.py`（1247 行）按上表拆开后，单个文件不再同时负责输入、状态和决策。

### 7.2 App

| 目标模块 | 职责 | 现在散在哪里 |
| --- | --- | --- |
| `transport` | 一个发送入口 `send(Outgoing)`、一个 sync 循环、一个后台请求包装；直连和中继只是两种线路 | `RuntimeClient.java`（1312 行）、`RuntimeRetry`、`MessageStream`、`Relay*` |
| `state` | sync 投影的本地副本，只读；不再自己保存置顶、归档、已读 | `HubStore.java`（1121 行）、`SyncCache`、`ChatHistory` |
| `screens` | 约 5 个页面：首页兼主对话、旁聊、在做的事（列表和详情）、帮手、设置；开发者入口单独一页 | `MainActivity.java`（4136 行，11 个页面） |
| `words` | 状态到界面文字的唯一翻译表（连接 3 种、任务 6 种、小幽活动 4 种） | 分散在各页面的字符串 |
| `device` | 蓝牙、设备屏幕、固件 | `BleLink`、`BuddyProtocol`、`Firmware*`、`LinkService` |

### 7.3 做法

- 先按模块搬家、不改行为，每搬一个模块跑一遍现有测试；再在新模块里按第 6 节的迁移顺序改行为。
- 电脑客户端与 App 共用同一份状态名和 `words` 翻译表，避免两端各自翻译。

## 8. 待主人决定

- 这个模型的边界：手机和设备是否也作为“感知来源”接入，还是只作为显示端。
- 主动说话的总原则：默认安静、只在承诺和关注上开口，还是允许她自己发现值得说的事。
- 投递优先级：设备、手机通知、主对话三者的先后，以及勿扰怎么设。
- 外部内容（手机通知、网页、电脑会话）的可信度规则：只当数据看，还是在某些情况下可以触发行动。
- 迁移第 1 步是否可以马上开始。
