# 小幽完整方案

状态：设计方案，2026-10-23；产品方向已确认，以下实现与验收尚未完成。

## 1. 你只需要和小幽聊天

手机、电脑、随身设备面对的是同一个小幽。你可以接着聊、交代事情、补充要求、停止任务；小幽负责选择能做事的电脑，把结果带回原对话。想指定电脑时，在对话里说即可。

核心原则是**尽量简洁**：一件事只有一个入口、一条处理路径；系统能决定的事，不交给你配置。正常时安静，出了问题说清楚发生了什么，并给出一个可执行的下一步。

界面只保留五处：

| 入口 | 内容 |
| --- | --- |
| 主对话 | 打开就能聊天；顶部显示忙碌中的帮手 |
| 旁聊 | 抽屉里新建和切换，空对话不保留 |
| 在做的事 | 只列交给帮手的任务，按等你确认、进行中、已结束分组；详情是一条时间线，可补充要求 |
| 帮手 | 每个帮手一项，显示忙闲和额度；在哪台电脑是内部属性 |
| 设置 | 小幽配对、随身设备、添加电脑、偏好；技术信息放开发者页 |

手机和电脑使用相同页面与措辞。随身设备保留头像、聊天、任务、用量四屏，不重写固件协议，也不更换现有帮手。

首次配对扫码，并在电脑上确认一次。之后自动连接、切网和重连，不显示地址列表，也不需要选择哪台电脑回答。连接问题只提示“连不上，请重试”“需要重新配对”或“需要更新”；单个功能失败就在该功能处提示。

## 2. 服务端只走一条处理路径

每台电脑运行一个 Runtime，负责本机帮手和持久记录；各节点同步记录，共同提供小幽。手机和电脑界面负责显示、发送和保存离线队列，中继只转发密文、帮助发现。

一次输入沿同一条路径处理：

**收到输入 → 保存记录 → 决定怎么办 → 保存决定 → 回复 → 执行结果回到原对话。**

- **先收好。** 用户消息、帮手结果和系统变化都进入同一份事件记录。保留来源、原始发生时间、所属对话，以及是谁、因为什么做了这件事。当前状态从记录生成，不再让多个模块各存一份答案。
- **先定，再说。** 决定要交办、记住或提醒时，先检查权限并持久保存任务或承诺，再把实际接收结果交给说话阶段。后台执行不等待回复生成或投递成功；回复只能描述真实状态，不能把“已排队”说成“已完成”。闲聊只产生消息，不创建任务。
- **有始有终。** 任务完成、失败或被停止，都保存结果并在原对话里回应一次。重启后从持久记录恢复，不能丢掉已接收的工作，也不能因为重放事件再执行一次。
- **接得上话。** 每个对话保留当前话题、未完成的承诺和相关历史。长期记忆只放偏好、规矩和长期情况；版本、在线状态、任务进度从当前状态读取，过期或未知就如实说明。

外部通知和观察到的电脑会话都是资料，不是用户命令。新增感知只增加事件适配器；是否行动仍经过同一套决策和授权。默认只在已答应或明确关注的事情有结果时主动开口，本轮改造不新增主动功能。

## 3. 多台电脑也只做一遍

**换连接不等于重新执行。** 每个请求保存稳定编号和负责它的节点；任务、承诺及其结束回复也有唯一负责节点。其他节点保存副本、转交指令，不各自执行或唤醒一次。

- 手机发出前保存请求编号、内容和接收节点。断网时可以继续输入；恢复后按顺序发送。同一编号的重传返回同一个结果；新编号即使文字相同，也是一条新消息。
- 回执丢失时查询原节点。其他节点可以代转；原节点不可达或执行状态未知时，显示等待并保留请求，不擅自换一台重做。尚未发出的新请求可以选另一台就绪节点。
- 同一对话按已接收顺序处理。已完成回合换电脑接续前，先补齐该对话的记录和未完成事项；有争用或未知回合就先协调。进行中的工具任务留在原执行节点。
- 每条记录仍由产地修改。审批绑定具体节点、任务、运行批次、操作和有效期；界面上的允许或拒绝只是向执行节点提交答案，不能扩大权限。

任务只用六个状态：`queued`、`running`、`waiting`、`done`、`failed`、`cancelled`。正常从排队到运行，等待确认后可以恢复运行；无需确认就直接结束。排队或等待期间也可以失败或确认取消。终态由执行节点持久确认，旧事件不能覆盖；停止请求未确认前显示“正在停止”，不能提前宣布已停止。完成与取消竞争时，以执行节点确认的终态为准。

这些归属都由系统保存，不增加用户要选择的角色或设置。第一版不做执行中任务的自动迁移。

## 4. 消息始终在原对话，通知按需出现

普通回复和任务结果先保存到原对话，再同步到各端。用户主动提问照常回复；旁聊不跳到主对话，勿扰不拦截对话内的回答。

主动提醒才选择通知方式：设备在身边就由设备播报；否则 App 在前台就在原对话提示；其他时候只有审批和到点提醒发手机通知，其余等用户回来查看。勿扰时只主动通知审批。

消息保存、通知送达、设备播放分别记结果。重连可以补齐消息，但不能因为重复同步而反复通知或播报。图片上传、语音识别失败在所属气泡重试。

## 5. 一份同步数据，一套接口

客户端从同一个同步入口获得消息、任务、会话、帮手、电脑、审批和小幽的活动状态。置顶、归档、已读也由服务端保存；客户端只保留副本和待发送内容。

| 接口 | 用途 |
| --- | --- |
| `GET /v1/info` | 身份、版本、最低支持版本、能力 |
| `GET /v1/sync` | 所有界面状态和消息更新，包括未完成的回复 |
| `POST /v1/messages` | 文字、语音或图片消息，携带请求编号和所属对话 |
| `POST /v1/files` | 上传图片和录音 |
| `POST /v1/actions` | 审批、停止、补充要求和对话整理；携带幂等编号，由认证身份确定操作者 |
| `GET /v1/tasks/{id}/timeline` | 分页读取任务时间线 |
| `GET /v1/artifacts/{id}` | 下载附件 |
| `/v1/dist/*` | App 与固件更新 |

同步沿用统一消息模型：按身份和修订号合并，数据与游标一起保存；缺口或游标失效用快照补齐，不删除更早的历史。切换节点先校验来源和同步进度，旧连接的回调不能污染新连接。未完成回复是快照替换，终态不能被旧片段覆盖。

附件引用携带来源、摘要和大小，经授权的加密通道按需获取，支持有界续传。消息换到另一节点处理前必须能读取所需附件；只有引用不算上传就绪。来源不可达就保留等待或说明失败，不当成无图消息继续处理。

复用现有记录中心、节点转交和加密传输，不再建设第二套。代码按事件、当前状态、对话与承诺、决策执行、帮手适配、接口分工，每份状态只有一个写入口。客户端保留传输、状态、页面、设备四个职责，显示措辞共用一份。

## 6. 实施顺序

每步可以独立验证和上线，保持现有功能可用。先明确执行与恢复约定，再整理模块；不以搬文件代替行为验证。

| 步骤 | 完成什么 |
| --- | --- |
| 1. 说做一致 | 删除暗中追问；落实先保存决定再回复、任务终态回流和操作者记录；实测首个回应 |
| 2. 一份状态 | 分开聊天与任务；统一任务状态、对话整理、当前话题和承诺；逐步收拢到唯一写入口 |
| 3. 自动连接 | 落实请求归属、重试去重、节点切换、附件获取、离线队列和版本协商，再去掉手选电脑 |
| 4. 收敛界面 | 客户端切到统一接口和五处入口，最后删除旧路径 |

旧接口在仍受支持的客户端迁移完成前保留。升级和回退必须保留配对、历史、审批和待处理请求；更新入口不能被版本门槛挡住。手机已有的整理标记幂等导入并确认后才删除本地权威副本。保留兼容的上一版程序和数据恢复路径。

## 7. 怎么确认改好了

每步按[跨端可靠性规则](cross-stack-reliability.zh_CN.md)验证和报告，构建成功不代表体验通过。至少覆盖：

- 同一请求收下后丢回执、切节点、重启，仍只执行和回应一次；不同编号的相同文字不合并。
- 断网发送三句后有序恢复；两端同时发消息、旧游标和迟到片段都能正确收敛。
- 任务执行中停止、审批后继续、完成与取消同时发生，以及负责节点离线，都显示真实状态。
- 在旁聊和勿扰时主动提问仍在原处收到回复；任务结果只通知一次。
- 图片在一台上传、另一台处理；来源离线时不丢消息、不忽略附件。
- 真实模型和网络下，文本、手机语音、设备语音的首个有意义回应在发送后 3 秒内显示；超时如实报告，排队提示不计成功。
- 混合版本、升级回退、冷启动和断线恢复后，配对、历史和待处理事项保留，多端状态一致。

完整测量、样本数和故障矩阵按可靠性规则执行。交付分别报告构建、主机测试、设备测试、回归、首个回应、连接恢复、多端同步和未验证项。
