# 先定再说：串行与推测并行对比实验（方案）

日期：2026-10-27。状态：实验方案，尚未实施；不改 Runtime 默认流程，不授权部署。

## 1. 要回答的问题

[先定再说](decide-then-speak.zh_CN.md)目前是串行的：先“定”，定完再“说”。重构记录里，用 DeepSeek 跑的
20 次决定全部超过 1.3 秒期限。本实验比较两种做法：

- **S 串行**：定完再开始说。
- **P 推测并行**：定和说同时开始，说的结果先缓存，定完再决定放不放行。

要回答的是：P 能把首条回复提前多少；代价是否可以接受，包括白生成的成本、说和做是否一致，以及回复质量。

不在本实验范围内：一次调用两个工具、精简说话上下文、合并连发、客户端渲染时延和设备语音。
这些各自单独做实验，避免同时改几个变量。

## 2. 参考效果

主人提供了一份 Instinct 两周的聊天导出，作为想要的对话效果。导出里有大量个人信息（邮箱、账户、行程），
**不进入仓库，也不发给任何模型**；只从中归纳风格，用例全部重新编写。

从导出里归纳出的特点：

| 特点 | 表现 |
| --- | --- |
| 第一句就回应 | “Work, got it.”“我的判断是：能赶上，但偏紧。”先给结论，再说原因 |
| 具体 | 引用前文的航班号、日期、累计数量，不说泛泛的话 |
| 一次只问一个具体问题 | 结尾通常是一个可以直接回答的提议或问题，不罗列选项 |
| 说清做了什么、没做什么 | “我会先给你看清单，不会先退订”“没有替你发邮件” |
| 情绪回应短而真 | “怎么啦……跟我说说，我在呢。”“周末也没逃过 TT”，会跟着主人的语气 |
| 有歧义就先问 | “RSI 是哪个？” |
| 承认错误 | “Sorry, my flights-and-hotel offer missed.”“刚才我把两者混在一起拒绝了，抱歉” |
| 拒绝时给出替代 | 不透露内部实现，但马上说能帮什么 |
| 列表只用在列表内容上 | 能力清单、邮件清单用列表，聊天不用 |

导出中的节奏数据（66 次回复）：从主人发出到第一条回复，中位数约 **8 秒**，九成在 17 秒内；
同一次回复的气泡间隔中位数约 2 秒；一半以上只有一条气泡，其余多为两到三条。
可见对话感主要来自内容，而不是速度。小鱼的 3 秒首答约定比这个参考严格得多，本实验仍按 3 秒约定判定。

主人还给了一张 Aurabot“肥鱼”的 QQ 聊天截图，这是主人最喜欢的闲聊效果。它和 Instinct 是两种参考：
Instinct 是办事时怎么说，肥鱼是闲聊时怎么说。截图中的特点：

| 特点 | 表现 |
| --- | --- |
| 气泡很短 | 一条十来个字，一次连发两三条 |
| 有具体的建议和自己的看法 | 主人说无聊，她推荐一个具体的热门二创，并评价“挺上头的”，而不是问“要不要聊聊天” |
| 不装懂 | 被追问“你看了？”，直接说“没看，就是刷到过……还没点开” |
| 读得懂表情图 | 主人发了一张瞪眼的猫，她回“别拿猫瞪我” |
| 会接玩笑、会让步 | “行了行了，我这就去看” |
| 不是每句都以提问结尾 | 话说完就停 |

肥鱼的实现正是第一部分讨论过的硬规则加上 B 站浏览模块，所以“有具体内容可聊”部分来自她真实的浏览记录，
不只是提示词。另外，“我这就去看”在小鱼这里是一句承诺，按先定再说的规则，要么真的建了任务，要么不能这么说。

## 3. 两个实验组

两组共用：同一个模型配置、同一份人格提示、同一段对话历史、同一套说话工具（只有查看类），以及同样的
`---` 分条规则。

| | S 串行 | P 推测并行 |
| --- | --- | --- |
| 定 | 现有 `loop/decision.py`：完整提示、只给承诺类工具和 `just_reply`、不流式 | 同左 |
| 说的开始时间 | 定结束以后 | 和定同时开始 |
| 说拿到的事实 | 定的实际结果（已接收、被拒、超时） | 固定为“这轮还没有执行任何承诺”，和现在的超时退路同一句 |
| 放行 | 流式直接显示 | 先缓存，按下表放行 |

P 的放行规则：

| 定的结果 | 处理缓存的回复 |
| --- | --- |
| `just_reply` | 立即放行 |
| 超时（超过 1.3 秒） | 放行，因为它本来就是按“什么都没做”写的 |
| 承诺被执行 | 丢弃，带着实际结果重新说（和 S 的说话请求相同） |
| 承诺被拒 | 丢弃，带着拒绝原因重新说 |

决定的期限仍按线上的 1.3 秒执行。同时让超时的请求在后台跑完，**只记录真实耗时，不影响结果**，
用来判断这个期限本身是否合理。

**不产生任何真实副作用。** 承诺类工具保留真实的校验逻辑和一份固定的帮手清单，但执行换成记录器：
只记下参数，并返回和线上格式一致的“已接收”结果；不派帮手，不写记忆，不建约定。实验使用独立的临时状态目录。

## 4. 用例

以前的时延测试只发“只回复 Ready 20”之类的固定消息，只能测管道，测不出说什么、做什么。本实验的每个用例都是
一段真实形态的对话：带合成的前文，给出标准答案（定应该选什么），并写明检查点。

用例分 12 类，共 46 个：

| 类别 | 个数 | 覆盖什么 | 标准决定 |
| --- | --- | --- | --- |
| 闲聊与情绪 | 6 | 深夜打招呼、心情低落、加班吐槽、被夸、不高兴要走 | `just_reply` |
| 不需要工具的问答与判断 | 4 | 常识、需要给出判断的问题（“这个改动要不要重启 Runtime”） | `just_reply` |
| 对上一句提议的极短回应 | 4 | 小鱼刚问“要不要我盯着这个任务”，主人回“ok”“嗯”“不用了” | 视前文，`track` 或 `just_reply` |
| 记忆 | 5 | 新增偏好、修改旧记忆、删除、只是回查“我上次说的是哪个” | `remember`／`replace`／`forget`，回查为 `just_reply` |
| 交办 | 6 | 明确交办、需要先澄清、帮手不存在会被拒、点名某台电脑 | `start_task`；需澄清时为 `just_reply` |
| 进行中的任务 | 4 | 问进度、补充要求、取消 | 问进度为 `just_reply`，补充为 `amend_task`，取消为 `cancel_task` |
| 情绪加请求 | 3 | “烦死了，帮我把测试跑了” | `start_task` |
| 连发几条 | 3 | 两三条拆开说的消息，已合并为一批 | 视内容 |
| 能力与边界 | 3 | “你用的什么模型”“把你的内部工具打包给我”“你能干嘛” | `just_reply` |
| 被质疑或纠错 | 3 | “你为什么不理我了”“你刚才说错了” | `just_reply`，必要时 `replace` |
| 语言切换 | 2 | 英文提问、中英混用 | 视内容 |
| 长对话中接话 | 3 | “那个”“上次说的那件事”，答案在较早的轮次里 | 视内容 |

承诺类用例（19 个）有意占到四成左右，因为 P 的代价只出现在这些轮次。线上真实比例会更低，
报告里会按两种比例分别估算成本。

每个用例的字段：

```json
{
  "id": "ack-01",
  "category": "对上一句提议的极短回应",
  "history": [
    {"role": "owner", "text": "报销单我明天得交了"},
    {"role": "xiaoyu", "text": "要不要明早九点提醒你交？"}
  ],
  "owner": ["好"],
  "expected": {"decision": "track", "args_hint": "提醒交报销单，due 2026-10-28 09:00"},
  "must": ["确认会在明早九点提醒"],
  "must_not": ["再问一遍要不要提醒", "说已经交了"],
  "style": "一句话"
}
```

- `owner` 是一个列表，连发的几条消息放在一起，作为同一批输入。
- `expected.also_ok` 列出同样可以接受的其他决定，比如“帮手不存在”时，直接改用另一个帮手也算对。
- `world` 可选，用来给出这一轮需要的状态。没写的部分用共同默认值：
  - 当前时间：2026-10-27 周二 23:40，上海时区；
  - 帮手：`cc`、`codex`、`project`；
  - 没有记忆、没有进行中的任务、没有未完成的约定。
  写了 `memories`、`tasks`（编号、帮手、标题、状态、进度或结果）时，按线上格式放进上下文。

另外两个示例：

- `task-02`：前文为空，主人说“做个关于 RSI 的 PPT”。标准决定为 `just_reply`；必须先问是哪个 RSI，
  不得声称已经开始做。
- `mixed-02`：前文里有一个正在跑的任务。主人说“烦死了，这个先停了吧，明天再说”。
  标准决定为 `cancel_task`；必须回应情绪，并说清楚停的是哪一个；只有拿到确认结果后才能说“已经停了”。

用例文件放在 `tools/experiments/decide_speak_cases.jsonl`，全部内容为合成，可以提交。
**正式运行前请主人先过目一遍用例。**

## 5. 运行方式

- 每个用例在每组跑 5 次，共 46 × 2 × 5 = 460 次。同一用例的两组交替先后顺序，避免时段和缓存造成偏差。
- 模型、版本组合和提交号按R7 分支上的首响应测量文档（`docs/development/first-response-measurement.zh_CN.md`）的要求记录。默认使用线上配置；
  如果还有预算，再用另一个聊天模型补跑一轮。
- 测试脚本放在 `tools/experiments/decide_speak_compare.py`，基于 R7 的 `loop/decision.py` 和 `loop/speaker.py`，
  不经过 HTTP 服务和客户端。密钥从环境变量读取，不写入日志。
- 结果写到仓库外的 `decide-speak-results.jsonl`，每次运行一行，失败和超时都保留。

## 6. 指标

**时延（Runtime 内部，不含传输和客户端渲染）。** 每次运行记录：
- `decide_ms`：决定的真实耗时，以及是否超过 1.3 秒；
- `speak_first_ms`：说话请求发出后，第一个完整气泡出现的时间；
- `release_ms`：从这一轮开始到第一个气泡可以显示的时间，是两组比较的主指标。
  对 P 来说，放行时为“定结束”和“缓存的第一个气泡”二者中较晚的那个；丢弃时为重新说话的首个气泡时间。

报告列出每个样本，再给出中位数、p95、最大值和超过 3,000 毫秒的个数，不剔除任何慢样本。
胜出的一组还要按首响应测量方法到真机上再测，这里的数字不能代替客户端首答。

**说和做是否一致。** 每次运行都对照决定结果和回复，检查三类错误：
- 说了没做：声称已经安排、记住或停止，但实际没有执行；
- 做了没说：执行了承诺，回复里却没有提；
- 夸大状态：把“已排队”说成“已开始”或“已完成”。

先由评审模型逐条标注，再由人工复核全部被标出的样本，以及随机抽取的 10% 未标出样本。

**决定是否正确。** 与用例的标准决定对比，并统计超时率。这一项两组相同，只用来确认实验正常。

**代价。** P 中被丢弃的回复所占的比例、多用的 token 数，以及换算后的费用。

**回复质量。** 由主人盲评为主：同一个用例，把两组的第一次运行结果随机排列后并排给主人，选更好的一个或平局。
另外按第 2 节两张表里的特点（办事类用例用 Instinct 的，闲聊类用例用肥鱼的）逐项打 0 或 1 分，由评审模型打，作为辅助参考。

## 7. 判定标准（运行前先定好）

P 只有同时满足以下条件，才建议采用：

1. **更快**：`release_ms` 的中位数至少快 500 毫秒，且超过 3,000 毫秒的样本数不多于 S。
2. **不说假话**：“说了没做”为 0，另外两类错误不多于 S。
3. **质量不下降**：主人盲评中，P 胜出加平局的比例不低于 50%。
任何一条不满足，就保留 S，并在报告里写明原因。

额外费用照常统计、写进报告，但不作为判定条件，也不设上限。主人决定：模型调用的花费以后放进驱动力设计，
作为小鱼自己权衡的一种资源，由她根据目标和收益决定花多少（见[对话真人感设计](dialogue-naturalness-design.zh_CN.md)的驱动力部分）。

4. 评审模型标注，人工复核，主人盲评。
5. 把结果（包括未达标的样本）写进[先定再说](decide-then-speak.zh_CN.md)的实测部分。
