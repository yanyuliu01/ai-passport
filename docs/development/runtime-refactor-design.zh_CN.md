# Runtime 三层重构设计

状态：设计已确认，2026-10-23 补齐实现契约。R1～R4 和 R5 的 Runtime 部分已提交，见第 7 节；R6 已补执行恢复、从消息构建上下文、共用对话队列、决定／操作持久化边界及分段摘要候选，默认流程仍未验收；R7 目录搬迁、循环导入清理及直接跨层依赖清理已实现；R8 按能力协商迁移客户端已实现，删除旧接口和 R6 默认切换仍受验收门槛约束。第 7 节分别记录源码、部署和验收状态。

本文把[小幽完整方案](xiaoyou-agent-model.zh_CN.md)落到 Runtime 代码上，按三层写：**状态接收层**（东西怎么进来、存成什么）、**回复消息层**（回复怎么生成、怎么送到各端）、**agent loop**（小幽怎么决定、怎么做）。问题编号指[交互简化问题清单](app-runtime-simplification.zh_CN.md)。所有阶段都要满足[跨端可靠性规则](cross-stack-reliability.zh_CN.md)。

## 0. 总览

```
             ┌──────────── 1. 状态接收层 ────────────┐
输入适配器 ──▶ Intake.accept(事件) ──▶ 事件日志 ──▶ 当前状态（投影）
 (HTTP/帮手/电脑会话/                    │              │
  其他电脑/定时/授权)                    │              ▼
                                         │      ┌── 3. agent loop ──┐
                                         │      │ 唤醒 → 定 → 记下决定 │
                                         │      │ → 执行/入队 → 说     │
                                         │      └────────┬─────────┘
                                         │               │ 结果也是事件
                                         ▼               ▼
                              ┌──── 2. 回复消息层 ────┐
                              │ 快照+增量 /v1/sync   │ ──▶ 手机 / 电脑 / 设备
                              │ 投递规则（通知、设备）│
                              └──────────────────────┘
```

设计借鉴了 Raft 和 DS-Bot-App 的部分做法，见第 8 节。

三条贯穿全文的规则：

1. **只有 Intake 能写事件日志。** 其他模块只读当前状态、只通过提交事件改变它。
2. **先存后做。** 任何输入、决定、结果都先作为事件持久化，再触发后续动作；重放只恢复状态、不执行外部动作；待办继续执行，结果不明的动作按第 1.5 节核对。
3. **客户端只看一份投影。** 消息、任务、会话、额度、授权、小幽在做什么，全部从 `/v1/sync` 一条路下发。

## 1. 状态接收层

### 1.1 目标结构

```
适配器（只读外部、只产出事件）
  HttpAdapter      你发的消息、语音、文件、写操作（/v1/messages、/v1/files、/v1/actions）
  HelperAdapter    帮手进展、结果、结束（取代 Tasks 里直接写卡）
  DesktopAdapter   观察电脑上的 Codex / Claude 会话（只读、幂等）
  MeshAdapter      其他电脑同步来的记录和指令
  TimerAdapter     到点提醒、关注条件
  SystemAdapter    额度、部署、版本、在线状态
        │
        ▼
Intake.accept(event) ── 去重、校验、写日志、推进当前状态、通知订阅者
        │
        ├── EventLog（cards.log.jsonl 的演进，唯一权威记录）
        └── World（当前状态投影：请求、任务、会话、电脑、帮手、授权、额度、焦点、承诺）
```

### 1.2 接口

**事件格式**（所有来源一致）：

| 字段 | 说明 |
| --- | --- |
| `id` | 稳定事件身份：客户端请求保留 `client_id`，内部事件用产地 Runtime 和产地序号；身份作用域见下文；内容一致的重试返回原接收结果（只按身份去重） |
| `seq` | 本机日志序号，单调递增，同步游标用它 |
| `at` | 原始发生时间（N9） |
| `source` | `owner` / `helper` / `desktop` / `mesh` / `timer` / `system` |
| `kind` | `said`、`action`、`task_progress`、`task_ended`、`session_observed`、`approval_requested`、`approval_answered`、`assistant_message`、`usage`、`deployed` … |
| `conversation`、`subject` | 属于哪个对话、关于哪个任务 / 会话 / 电脑 |
| `actor`、`cause` | 谁做的（`app`、`desktop`、`xiaoyou`、`mesh:<节点>`、`cli`、`system`）、因为哪个事件（A4） |
| `trust` | `owner` / `system` / `helper` / `external`；`external` 只当资料，永远不会变成主人的话 |
| `payload` | 各 `kind` 自己的内容 |

**Python 接口**（模块内）：

```python
Intake.accept(event) -> Accepted(id, seq, duplicate: bool)
World.get(kind, id) / World.list(kind, **filter)        # 只读
World.subscribe(after_seq) -> 事件流                     # agent loop 和回复层用
```

**身份与权限：**客户端请求身份是 `(origin_runtime_id, authenticated_client_id, client_id)`；首次接收时由接收权威节点确定产地，重试保持不变。内部事件用 `(origin_runtime_id, origin_seq)`。同一身份的重试，其类型、对话、目标和归一化后的内容必须与原请求一致，否则明确返回冲突（HTTP 409），不执行，也不返回另一个对话的内容。比较内容是校验编号复用，不是按内容去重。返回已有结果前仍须认证和检查作用域。

Mesh 保留原始身份和修订；接收节点另分配本机 `seq` 用于重放，转发不能生成新身份。跨节点指令有自己的稳定身份和目标权威节点，副本不执行指令。发送方填写的 `actor`、`trust` 不构成授权，适配器根据认证来源确定实际权限。去重记录在约定重试窗口内必须跨重启和日志压缩保留；过期身份要明确核对，不能悄悄当新请求执行。

**三种代次和位置，不能混用**（评审修正，见 [runtime-refactor-review](runtime-refactor-review.zh_CN.md) 第 3 节）：

- `log_epoch`（沿用现有协议字段 `epoch`）：某个产地日志历史的代次，只用来判断游标还能不能接续。
- `owner_generation`：某段对话的负责人授予代次，由协调权威管理，只用来拒绝旧执行者（见 3.1）。
- `accepted_seq` / `applied_seq`：同一产地、同一日志代次里的持久接收位置和投影应用位置。本地持久接收不是 Raft 的多数派提交。

多产地的进度按 `(origin, log_epoch, seq)` 分别跟踪，不能拿两台电脑各自的序号比较谁更新。普通重启不重置持久身份和代次。名字是概念区分，不要求立即改现有兼容字段。

### 1.3 各来源的规则

- **你发的消息**：先 `accept`，再排进对话；回执只说“已收到，编号 X”。
- **帮手**：进展只更新任务的进展字段，不写主对话；结束一律产出 `task_ended`（完成 / 失败 / 已取消），交给 agent loop 收尾（A1）。
- **电脑会话**：只写进它自己的观察会话，永远不进主对话、不触发小幽说话；同一会话的同一修订重复观察不产生新事件；接话材料不能引用接话材料（N8、N11）。
- **其他电脑**：每条记录只由产地修改；对方发来的指令（取消、确认、转交）带 `actor=mesh:<节点>` 进入同一个 `accept`。
- **取消、确认等写操作**：统一是 `kind=action`，带 `actor` 和原因（A4）。

### 1.4 和现有代码的对应

| 现在 | 以后 |
| --- | --- |
| `Service.submit` / `submit_voice` / `_enqueue`、`Ledger`（`messages.json`） | `HttpAdapter` + `World` 里的“请求”投影；`messages.json` 变成可重建的快照 |
| `record.exchange` / `reply` / `request_changed` / `task`、`cards.py` 直接写 | 全部改为 `Intake.accept`；`cards.json` 变成投影快照 |
| `tasks.Control.activity`、`Xiaoyou._finished` 写卡 | `HelperAdapter` 产出 `task_progress` / `task_ended` |

| `Service.cancel`、`Xiaoyou.cancel`、`__main__` 中断、`mesh` 取消指令 | 一个 `action:cancel` 事件，`actor` 分别为 `app` / `cli` / `mesh:…` / `xiaoyou` |

### 1.5 持久接收与恢复

`Accepted` 表示输入和待执行意图已持久提交，不只是进入内存队列。Intake 串行完成校验、身份分配和持久追加；提交后才推进投影、通知订阅者。追加成功但回执丢失时，重试返回同一接收结果。重放必须确定且没有外部副作用；订阅者从持久游标恢复，并容忍重复投递。R3 前必须确定日志提交边界、尾部不完整记录的恢复、格式版本和保留/检查点规则；仅向 JSONL 追加一行不等于保证持久化。

每个可执行决定都有稳定的 `operation_id`，关联触发事件，并在执行前保存。记录 `pending`、`running`、`succeeded`、`failed`、`cancelled` 或 `unknown`，以及可获得的外部执行身份。同一操作只能由一个执行者领取；重启或领取期限到期，不代表外部动作已经停止。

| 故障边界 | 恢复要求 |
| --- | --- |
| 持久接收前 | 不返回已接收；使用同一身份重试 |
| 已接收、尚未开始执行 | 继续执行待办一次 |
| 外部动作可能已经开始、结果尚未提交 | 按执行身份查询，或使用提供方支持的同一幂等键重试；两者都不支持时标为 `unknown`，核对后才能重做 |
| 结果已提交、投递中断 | 重放已保存的结果，不重新执行 |

取消请求与确认取消是不同状态。完成与取消竞争时，按明确的终态转换表处理；迟到的进展不能让已结束任务重新运行。确认终态后，使用持久的触发/操作身份，在原对话逻辑上唤醒一次，重放不能重复播报。打断说话不会撤销已接收动作：保存回复被打断的状态，并明确取消或保留该操作。

R3 必须通过注入崩溃、重复投递和并发领取测试覆盖每个边界。保留的日志/检查点须能重建所有承诺恢复的状态，包括待办和去重记录。停写旧存储前验证旧数据导入及回退兼容性；测试中删除快照不能删掉历史的唯一副本。

## 2. 回复消息层

### 2.1 目标结构

```
assistant_message 事件（小幽说的每一段：块、格式、状态 streaming/final、修订号）
        │
        ▼
Projection（唯一的显示投影：presentation_v1 的演进，含格式片段）
        │
        ├── /v1/sync：快照 + 增量，所有端唯一的下行通道
        ├── 投递规则：在身边→设备；前台→原对话；否则只推“等你确认”和到点提醒
        └── 其他电脑：经 Mesh 复制同一批事件
```

### 2.2 接口

**同步**：

```
GET /v1/sync?cursor=<游标>&wait=<秒>
  → { epoch, cursor, more, snapshot?, events[] }
```

- **发现缺口时先补增量，游标失效或增量已不保留时才给快照；游标为空时直接给快照，不重放历史。** 快照只包含当前状态：每个对话最近 N 条消息、所有未结束任务、未处理授权、额度、小幽状态。然后从快照边界开始给增量。目标是在认证连接就绪后 1 秒内显示当前对话，需实测验证，不再要追 415 页（N10）。更早的历史按需分页取（`GET /v1/conversations/{id}/history`）。
- **页大小按条数定**，不再是 48 KB；单条过大的内容（长回复、附件）只给摘要和引用。
- **客户端把已应用状态和游标原子保存**，重启后接着追；只存游标可能跳过尚未应用的事件。
- **正在生成的回复**也是 `assistant_message` 事件，`status=streaming`，每次整段替换；`final` 后旧片段不能覆盖。客户端不再为单条消息另开等待循环或推送流（C1、C9）。
- **长连接**：`wait` 有变化立即返回；以后要换成推送流（SSE / WebSocket）也只是换传输，事件格式不变。

**快照边界和总量：**每个游标和回调都绑定 Runtime 身份、epoch、授权作用域和连接代次。快照固定在序号 S，用稳定的快照令牌分页，保留 S 之后的增量；作用域内快照应用完成后才切到实时投递。S 之后的增量只在有界的保留窗口内保留；慢客户端超出窗口就重新取快照，不为等所有客户端而无限保留日志。令牌失效或所需增量不再保留时，明确重新核对。丢弃旧连接回调；删除标记防止已删除项目再次出现。

50 条是每个对话的上限，不代表一次返回所有对话。先加载当前对话、相关任务和待处理授权，其余已授权状态分页并显示加载进度。条数限制之外还要有明确的字节/处理量上限和续页令牌。超大内容的引用必须可取回，摘要不能悄悄替代权威正文。切换作用域时先核对再标为最新。测试长历史、快照与增量竞争、来源切换、本地提交失败和游标过期。一秒目标针对当前可见状态；整体恢复和传播仍须满足共享的三秒契约。

**发送**：

```
POST /v1/messages { id, conversation, text | audio_ref | image_refs } → { id, accepted: true }
POST /v1/actions  { id, type, target, reason } → { id, accepted: true }
```

只返回“已收到”。处理状态、回复、结果全部经 `/v1/sync` 到达。

**显示**：投影给出块边界、格式片段（加粗、斜体、代码、标题、链接、列表、引用）和作者，各端只按投影渲染，不自己解析 Markdown（N13）。

### 2.3 和现有代码的对应

| 现在 | 以后 |
| --- | --- |
| `Service._report("partial")`、`_update`、`_snapshot`、`get(wait, rev)` | 产出 `assistant_message` 事件；`get` 只为旧客户端保留 |

| `proactive.py` 里“说不说、在哪说” | 投递规则（本层），“要不要开口”留在 agent loop |

## 3. Agent loop

### 3.1 目标结构

```
唤醒规则（订阅 World 的事件，确定、便宜）
  owner said ─────────────┐
  task_ended（我派出的） ──┤
  关注条件满足 ────────────┼─▶ 对话的一步 step(conversation, trigger)
  承诺到点 ────────────────┘
                             1. 组上下文：焦点 + 未完成承诺 + 最近对话 + 相关检索 + 自身状态
                             2. 定：一次调用，只选一个动作
                                reply / dispatch / amend / cancel / watch / promise / remember / stay_silent
                             3. 记下决定：accept(action 事件)（先存后做）
                             4. 执行有界的本地动作，或把长任务持久入队；保存实际结果或接收状态
                             5. 说：一次流式调用，只有查看类工具，按已保存状态据实回复；
                                长任务结果稍后作为事件回到第 1 层
```

- **主动和被动是同一个 `step`**，只是触发不同。新增主动能力 = 加一条唤醒规则。
- **任务结束必然唤醒**：完成、失败、取消都会让她在原对话说一句（A1、M3、N12）。
- **一轮只说一次**：没有暗中追问（已删），没有“写 JSON 失败再问一次”的重说路径；动作不合法时照实说办不了。
- **并发**：同一对话的“定”串行；你在她说话时又发一句，打断正在说的那段（沿用现有打断），新消息排在下一步。不同对话互不阻塞。
- **在哪台电脑做**：`dispatch` 时按帮手所在、目录可达、额度、在线情况选择；你点名的优先。
- **对话负责人（第一版）**：每段对话绑定一个持久、明确的负责人；首次绑定经指定权威完成，不由各节点各自猜。网络超时只说明不可达，不证明原负责人已停止，所以**不因超时自动换负责人**。负责人不可达时保留请求和原编号，显示“排队 / 负责人不可达”，区分本地待发和权威已接收，不声称已开始；旧任务不迁移，按操作身份查询，核对不了的标为结果不明。人工“接管”同样要满足下面的隔离条件。自动接管要等协调权威、授予、写入隔离、模型结果失效、外部工具隔离、协调方故障和时钟规则都写明并通过故障测试后才启用（评审第 2 节）；R4 落实授予和写入隔离，R6 接入模型和执行路径，不能先自动切换、后补拒绝。
- **确定性核心**：状态归约是“旧状态 + 已保存事件 → 新状态 / 待执行意图”。时钟、随机身份、模型返回、网络结果、工具结果都是显式输入，需要恢复的输入要保存。重放**不调用模型、不执行工具、不发通知、不重新生成决定**；模型请求和工具执行由外层驱动，结果作为事件回到状态机。投影状态和 `applied_seq` 一起保存（评审第 4 节）。
- **自查工具**：版本、部署、在线、进行中的任务直接读 `World`，不派帮手去查（M1、M2）。

### 3.2 接口

```python
Loop.step(conversation, trigger: Event) -> None
ContextBuilder.build(conversation, trigger) -> Context
Decider.decide(context) -> Action            # 先定；超时走 decide-then-speak 文档里的退路
Speaker.speak(context, action_result) -> 流式 assistant_message 事件
Executor.apply(action, operation_id) -> ActionResult  # 已持久保存的本地结果或入队回执
HelperPort.run(job, control) -> 进展与结果事件  # Claude Code、Codex、DeepSeek、远端节点
```

`ActionResult` 区分本地操作完成、已入队、远端确认开始、失败和结果不明。入队只允许说“已排队”，不能说“已开始”或“已完成”。慢的外部调用在工作线程执行，不阻塞首个回复。后续终态事件产生单独的完成轮次；“一轮只说一次”不抑制这条结果。仅回复的动作无需执行外部操作。

启用两次模型调用的路径前，把端到端 3,000 ms 统一预算分配到排队、上下文、决策、有界执行、生成、传输和客户端显示。测量首个有意义的完整气泡，不是 HTTP 回执、首 token 或固定应答。按共享采样/故障矩阵使用真实模型和已安装客户端测试。慢决策和查看工具共用原始期限；延迟/不可用提示只算恢复反馈，不算时延通过。候选路径达标前保留受支持的路径；删除回退以证据为门槛，不以计划日期为门槛。

## 5. 兼容与风险

- **日志格式只增不改**：旧字段保留，新字段可缺省；旧版 App 在 R8 之前照常可用。
- **多台电脑版本不一**：其他电脑可能还是 0.20.0。新字段对它们是可忽略的；需要新能力时按 `/v1/info` 的能力判断，低于门槛时提示升级。
- **快照的正确性**：快照必须和增量来自同一个游标点，切换时不能丢事件；用“游标 + epoch”校验。
- **“先定，再说”的时延**：多一次模型调用，可能超过 3 秒；先实测，不达标用文档里的退路。
- **改造期间正在运行的 Runtime**：只改源码的阶段不影响现用进程。持久格式迁移后，回退需要兼容的程序和数据路径，仅切回旧代码不够。上线（重启）遵循主人的授权。

**R4.2 的做法：**

- **绑定记录。**负责人记成绑定记录（对话、负责人、代次），作为写它那台的记录随小幽网络同步（类型 `owner`）。代次和日志代次（`log_epoch`）分开。主对话的第 1 代由配置了 `mesh.home: true` 的那台写（主人把它设在 Mac 上）；旁聊的第 0 代是创建它的那台，记在对话目录的 `owner` 字段里，改名、同步都不改它；没记的旧旁聊归主对话的负责人。还没有任何绑定时照旧由收到的那台回答（和 R4.2 之前一样），所以 Mac 配好之前不会有人把主对话卡住。
- **谁能写下一代。**只有当前负责人能写下一代绑定，所以不需要另外的协调服务器：每台按同一个规则从记录里推出现在的负责人——第 g 代只认由第 g−1 代负责人写的；主对话第 1 代如果有两台都写了（配置错误），按 Runtime 编号取小的，并在状态里报冲突。
- **写入点上的隔离。**一句话在被工作线程领取时，在同一把锁里检查“这台还是不是负责人”：不是就转给负责人，不自己答。移交只在这段对话没有排队、没有正在处理的话、也没有进行中的事时，在同一把锁里写下新绑定，所以检查和写入之间没有窗口。帮手派到别的电脑上执行（`hop` 大于 0）、在某件事里面补充一句（`pin`）不受影响：进行中的事留在执行它的那台。
- **收到同步记录时的隔离。**一台写下“交出去”的绑定后，它之后再写的、属于这段对话的回复和新事，别的电脑收到时拒绝（按那台自己的序号判断，不看时钟）；交回给它以后照常接收。
- **连不上时排队。**转交时负责的电脑不在线：这句话保留原编号，状态仍是排队、操作仍是 `pending`，显示“排队中：负责的电脑「Mac」连不上”；它回来后按顺序交过去。转交的那条带上绑定记录，收到的一方先核对、更新自己的绑定，不会两边互相踢皮球；被转交来的话不再转第二次。
- **手动移交。**`POST /v1/conversations/<名字>/owner`，`{"to": "<那台的名字或编号>"}`。在负责人上调用就直接移交；在别的电脑上调用就转成给负责人的指令。两台都要在线；不满足空闲条件时拒绝并说明原因。
- 权限（R4.3，10-23 主人定）：权限权威是 Mac；每台设备单独凭据，旧的共享令牌在过渡期继续可用；回答授权、增删设备和电脑、移交负责人算敏感操作。R4.3 先只做 Runtime 部分，App 和电脑客户端另做一批。

**R4.3 的做法（Runtime 部分）：**

- **权限权威**就是写主对话第 1 代绑定的那台（配置了 `mesh.home` 的 Mac）；之后主对话移交给别人，权限权威也不跟着变。不在小幽网络里的 Runtime 自己就是权威。
- **主机身份**就是已有的 `runtime_id`（`state/runtime-id`）。以前这个文件坏了会悄悄换一个新的；现在只有文件不存在时才生成，坏了就拒绝启动并说明，因为换身份等于所有设备都要重新配对。`/v1/info` 给出身份编号和指纹。Runtime 没有可用的非对称加密库、自己也不做 TLS，所以证明身份用设备凭据：客户端带一个随机数来，Runtime 用这台设备凭据的哈希做 HMAC 回答，任何线路（局域网、私网、公开入口、中继）上都能核对。**它证明的是“连到的是主人的小幽网络里持有我凭据的 Runtime”，不能区分是网络里的哪一台**（凭据哈希会同步到每台）；要逐台证明，得在客户端那一批引入非对称密钥。证书续期、换隧道入口不改主机身份。
- **设备凭据。**配对时权威签发 `dev.<编号>.<密钥>`，只给一次；各台只存密钥的哈希，凭据随小幽网络同步（只认权威写的）。撤销也由权威记下、同步，撤销后各台都拒绝它。旧的共享令牌照常可用，等 App 和电脑客户端迁移完再停。
- **敏感操作。**回答授权、增删设备、移出电脑、移交负责人：不在权威上时，要权威当前在线（拿得到最新名单）才做，否则拒绝并说明“Mac 不在线”。聊天、查看、停止任务不受影响。增删设备、移出电脑本身只在权威上执行；在别的电脑上发起就转成给权威的指令。
- **移出电脑。**加入网络仍靠口令；权威可以把一台电脑移出，各台之后拒绝和它交换记录。
- **地址范围和手动线路。**每个地址标上范围：本机、局域网、私网（Tailscale 100.64/10）、公开入口。配置里手写的 `mesh.peers` 地址不会被自动发现的地址覆盖，认出是哪台以后排在最前面。

### 8.1 etcd-io/raft（多台电脑之间的数据一致）

不用 Raft 的选主和多数派，是一个可选的架构决策：第一版用“产地单写者 + 明确的负责人”来保证安全，不承诺负责人失联后的自动可用。这个选择**不能**用“家里只有两三台电脑，多数派没有意义”来论证；单写者的安全靠的是第 1.2 节的代次区分和 3.1 的负责人规则。

| Raft 的做法 | 我们怎么用 | 落到哪一步 |
| --- | --- | --- |
